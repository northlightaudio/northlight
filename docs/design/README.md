# Northlight design

The design source for Northlight: the brand, the design system, and a specification
for every screen, precise enough that the implementation can be checked against it.
Where the application and a spec disagree, the spec is the intent: fix the
application, or change the spec on purpose.

## How a screen spec reads

Each screen spec has the same shape:

1. **Purpose and anatomy**: what the screen is for, and a labelled list of its parts.
2. **Layout**: sizes in pixels at 100% scale, with tokens by name.
3. **Visual**: which tokens colour which part, in each state.
4. **Behaviour**: hover, press, drag and keyboard, and the empty, loading and error
   states.
5. **Acceptance**: the checks that prove the implementation matches.

Sizes are written `W×H` in px. Colours are token names, never hex, except in the
design system where the tokens are defined. "Accent" always means the interaction
colour (Overcast), never a track colour. A choice marked **Decision** was made
deliberately and records why.

## Rules for the implementation

- Nothing in `src/ui` carries a literal colour or size; everything comes from the
  tokens through `ui::Theme`. A check in the test suite enforces the colours.
- Stock controls are drawn by `NorthlightLookAndFeel`; dedicated components cover
  what stock controls cannot reach (fader, knob, meter, segmented control, clip,
  track header, ruler).
- A token change is checked with `python scripts/contrast.py --check`, and the
  contrast table regenerated.
- Brand files (the mark, lockups, app icon) are generated by
  `scripts/brand-assets.py`; never edit them by hand.
